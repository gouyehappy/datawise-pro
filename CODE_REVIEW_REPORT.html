总体结论

逐个模块深度审查并交叉验证后，得出三点核心判断：

1. 工程底座健康，但存在一组可被组合利用的高危缺陷

各模块普遍具备生产级设计意识：RBAC 分层、密码学用法、XSS/SSRF/路径遍历防护、SQL 参数化、AST 优先的 SQL 改写、资源生命周期管理都到位。未发现大面积失控或核心鉴权失守。但少数"边界与纵深防御"缺陷可被串联成真实攻击链，必须优先处理。

2. 三个架构级问题需要重构，其余为专项加固

需要重构：桌面端 JCEF 桥接层（信任模型缺陷，可组合成持久化 RCE）；DataAgent 的授权/并发治理（授权与实际执行 SQL 未绑定）；全产品"黑名单正则做安全决策 + 失败回退拼接"的反模式。其余模块点状修复即可。

3. 不建议推倒重来

缺陷高度集中在可收敛的几个点：URL/日志凭据泄露、动态 SQL 校验、token 膨胀、竞态与缓存治理。点状替换 + 配置默认值调整即可覆盖大部分，投入产出比高。若规划公有云 / 多租户部署，SSRF 与凭据泄露类问题的定级需整体上调。

重构与升级决策矩阵

模块架构健康度是否重构核心理由
桌面端 JCEF 桥接层弱必须重构信任模型不成立：把文件系统、JRE 路径、进程重启等原生高权限能力以字符串通道无条件暴露给 Web 渲染层且不校验来源，可组合成"外部页面 → 任意文件读写 → 恶意 java.exe → 持久化 RCE"完整链条。
DataAgent (datawise-ai)中定向重构工作流骨架优秀应保留，但授权体系（grant 未绑定 SQL、客户端可控跳过确认、TOCTOU 竞态）动摇写操作安全模型；熔断/缓存/grant 并发治理各自为政，缺统一租户隔离抽象。
动态 SQL 校验机制中专项替换关键词黑名单 + 解析失败回退字符串拼接，在 AI 模块、鉴权门禁、连接器三处重复出现，均存在绕过/误杀。应统一改为 SQL Parser + AST 白名单，禁用字符串回退。
后端安全 / 鉴权强安全加固架构成熟可控，无结构性缺陷；2 项凭据经 URL/日志泄露为 P1，改造成本低收益高，一个迭代内完成专项整改即可。
连接器 / 数据库层强安全加固SPI 插件化 + 方言隔离设计健康；问题集中在凭据散落泄露、驱动下载无校验、默认无超时 + 大结果集全量入堆，均为点状替换 + 配置默认值调整。
前端中上增量修复XSS 双重过滤、资源生命周期管理规范；真正要改的是异步错误处理一致性、竞态防护（重复提交、ECharts 白屏）、巨型组件拆分。无需整体重构。
生态（CLI/MCP/VSCode/插件）强无需重构工程质量与安全意识高，插件宿主边界是本项目质量最高部分之一；仅 token 传递、API URL 校验等点状修补。

分阶段修复路线图

阶段一 · 立即
止血（P0）
  • 桌面桥接层加 origin 白名单 + 来源二次校验
  • 移除/收敛 fs:registerRoot 与 JRE 路径字符串设置
  • 更新器补签名/哈希校验、固定更新源
  • JDBC 驱动坐标白名单 + 禁跟随重定向 + SHA256
  • 登录密码改请求体、OIDC session 改 fragment、日志 query 脱敏
  • AI grant 与 threadId/SQL 强绑定、关闭客户端 skip 开关
  • 迁移 WHERE / 排序列改 AST 白名单
阶段二 · 短期
加固（P1）
  • JDBC URL 统一脱敏管道（日志 + 响应）
  • 默认 License 密钥外部注入 + 强制 fail-fast
  • SQL 写权限判定改解析器
  • AI 关键词黑名单 + JSON 贪婪截取替换
  • 迁移 SSE / AI 发送竞态防护
  • 熔断器按租户隔离
阶段三 · 中期
治理（P2）
  • 统一缓存/限流/去重的租户隔离抽象
  • 查询超时默认值 + 大结果集流式导出
  • 凭据外发面收敛（CLI token、MCP URL、代理头）
  • 异常信息统一过滤、尝错误码化
  • 前端异步容错规范化
阶段四 · 持续
质量（P3 + 债务）
  • 巨型组件 / Store 按 composable 拆分
  • TypeScript as any 清零、JWT claims 补全
  • 静默降级补可观测性日志
  • 安全回归用例固化，防止迭代回退
